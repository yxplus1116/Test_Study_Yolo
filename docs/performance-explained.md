# 如何理解 GPU、FPS 和性能测试

**当前模型确实使用 RTX 3060 Ti，通过 TensorRT 在 GPU 上推理。日志里的 `fps` 是整个应用处理循环的平均帧率，不是显卡单独运行模型的速度。** 本机这次测得：预热后的模型执行约为 **1028 FPS**，GDI 采集并显示预览约为 **45.76 FPS**。两个数字衡量的工作量不同，可以同时成立。

当前流程是：屏幕采集 → CPU 图像预处理 → 上传到显存 → TensorRT GPU 推理 → 下载预测结果 → CPU 解码与去除重复框 → 目标选择 → 绘制和窗口事件处理。模型在 GPU 上执行，预处理与解码目前在 CPU 上完成；屏幕采集、数据传输和预览窗口仍然需要时间。DXGI 采集中的纹理复制等操作也会涉及 GPU。

默认从屏幕中央采集 `416×416` 的区域。这个区域随后会缩放、填充成模型需要的 `640×640`，转为 RGB、浮点数和三个通道的数据。因此，采集区域是 416，并不表示模型正在以 416 的输入尺寸推理。

本次测量使用 NVIDIA GeForce RTX 3060 Ti、TensorRT 10.6、CUDA 12.6 和项目中的 `workspace/cf.onnx`，模型输入为 `[1,3,640,640]`，一次处理一张图。引擎默认允许 TensorRT 优先采用 FP16；这不表示每个算子都强制使用 FP16。各模式顺序运行，没有同时启动多个测试实例，所有测试均关闭实际鼠标输出。

| 测量模式 | 实际测量内容 | 本次结果 | 原始记录 |
|---|---|---:|---|
| GPU 引擎基准 | 上传一次固定输入，预热 30 次，计时执行 600 次；不含采集、逐帧传输、CPU 预处理与解码、显示 | **0.973 ms/次，1028.14 FPS** | [gpu.json](D:/Projects/Test_Study_Yolo/docs/validation/menu-performance/gpu.json) |
| GDI，关闭预览 | GDI 实时采集及完整检测循环，运行约 5 秒 | **87.18 FPS**，436 帧 | [gdi-headless.json](D:/Projects/Test_Study_Yolo/docs/validation/menu-performance/gdi-headless.json) |
| DXGI，关闭预览 | DXGI 实时采集及完整检测循环，运行约 5 秒 | **127.70 FPS**，639 帧 | [dxgi-headless.json](D:/Projects/Test_Study_Yolo/docs/validation/menu-performance/dxgi-headless.json) |
| GDI，显示预览 | GDI 实时采集、完整检测循环及预览窗口，运行约 5 秒 | **45.76 FPS**，229 帧 | [gdi-preview.json](D:/Projects/Test_Study_Yolo/docs/validation/menu-performance/gdi-preview.json) |

**DXGI 的完整流程 FPS 还受桌面实际更新频率限制。** 随后从菜单选择“7 → 4”进行整组验证，在较静止的桌面上测得 GPU 模型 1146.43 FPS、GDI 89.55 FPS，而 DXGI 只有 **3.74 FPS**：8 秒内处理 30 个新帧，235 次空采样，采集错误为 0。这说明它主要在等待新画面，不能把 3.74 直接当作 GPU 的处理上限，也不能把上表的 127.70 当作任何场景下的固定帧率。菜单会提示 DXGI 空采样；测试会依次自动完成并保存[整组原始结果](D:/Projects/Test_Study_Yolo/docs/validation/menu-performance/menu-sequential-quiet-desktop.json)。

实时测试的 `fps` 计算方式是“成功处理的帧数 ÷ 采集循环经过的秒数”。它包含循环期间的等待和其他开销，但不包含先前加载或构建引擎的时间。`fps_recent` 表示最近一个报告区间的帧率，能更快反映当前变化；启动初期或区间很短时，数字容易波动。

下面是同一组实时测试的平均耗时，单位均为 **毫秒/帧**。数字越小，代表该阶段占用时间越少。

| 阶段 | GDI，关闭预览 | DXGI，关闭预览 | GDI，显示预览 |
|---|---:|---:|---:|
| 屏幕采集 | 4.523 | 1.136 | 5.466 |
| CPU 图像预处理 | 4.188 | 4.083 | 4.873 |
| 上传输入 | 0.598 | 0.488 | 0.572 |
| GPU 推理 | 1.256 | 1.262 | 1.329 |
| 下载预测结果 | 0.133 | 0.138 | 0.138 |
| CPU 解码及去除重复框 | 0.507 | 0.510 | 0.536 |
| 推理流程合计，含预处理、传输、推理和解码 | 6.906 | 6.652 | 7.697 |
| 绘制和提交预览 | 约 0 | 约 0 | 0.958 |
| 窗口事件处理及等待 | 0 | 0 | 7.493 |
| 成功处理一帧的循环计时 | 11.443 | 7.802 | 21.640 |

“推理流程合计”已经包含它上面的预处理、上传、GPU 推理、下载和解码，不能再把这些行全部相加。各阶段采用不同计时点，另外还有同步、调度、目标选择和日志等开销，因此子阶段之和、循环计时以及 `1000 ÷ fps` 不必完全相等。

本次显示预览时，窗口事件处理及等待约占 **7.49 ms**，屏幕采集约占 **5.47 ms**，CPU 预处理约占 **4.87 ms**；GPU 推理约占 **1.33 ms**。这组结果说明，这次运行中限制整体速度的主要部分在采集、CPU 处理和窗口显示。不能由整体只有约 46 FPS 推断“没有使用显卡”。

窗口代码使用 `cv::waitKey(1)` 处理按键和窗口消息。参数 `1` 不保证调用每次恰好只花 1 ms，操作系统调度和窗口消息处理也会计入实际时间。这里的 **7.49 ms 是本机本次实测值**，不是给其他设备设定的固定开销。

你此前看到的 `fps=51.8` 与本次 GDI 预览测量处在接近的范围，可以由当前完整流程的开销解释。桌面内容、窗口大小、系统负载和采集方式变化都会影响这个结果；单凭那一条旧日志，无法精确还原当时每个阶段的耗时。现在的日志会同时打印 `gpu_ms` 和 `capture_ms`，每帧详细数据会写入 `frames.csv`，结束后的平均数据保存在 `summary.json`。

**200 FPS 的完整应用要求平均每帧在 5 ms 内完成全部工作。** 这次即使关闭预览、采用 DXGI，CPU 预处理和 GPU 推理两个阶段合计已经约为 5.35 ms，还没有计算采集、上传、下载和解码。因此，在当前实现中，GPU 单独执行超过 200 FPS，并不会自动使整条流程也超过 200 FPS。

如果后续要提高完整流程的速度，可以先关闭预览并对比采集后端，再针对 CPU 预处理、重复分配和数据传输做优化。将预处理移到 GPU、复用缓冲区或减少显示更新频率都需要改动代码并重新测量；本次没有用一个更高的引擎基准数字代替这些优化，也不承诺尚未实现的帧率。

日常可从统一启动菜单选择性能测试，无需记住参数。下面的命令用于复现本报告的测量口径，在项目目录的 PowerShell 中逐条运行，前一条完成后再运行下一条：

```powershell
.\scripts\run.ps1 --benchmark --frames 600 --output .local/performance-menu/gpu
.\scripts\run.ps1 --capture gdi --headless --seconds 5 --output .local/performance-menu/gdi-headless
.\scripts\run.ps1 --capture dxgi --headless --seconds 5 --output .local/performance-menu/dxgi-headless
.\scripts\run.ps1 --capture gdi --seconds 5 --output .local/performance-menu/gdi-preview
```

GPU 基准使用同一条 CUDA 流，连续提交预热后的模型执行，通过 CUDA 事件计时。它仍可能受到其他 GPU 工作、显卡频率和主机提交间隔的影响；没有使用 CUDA Graph 来追求额外的极限吞吐。实时流程的上传、推理和下载同样用 CUDA 事件计时，CPU 阶段和完整流程用单调时钟计时；CUDA 区间也可能包含流的等待或提交间隙，不能等同于逐个 GPU 内核的分析结果。

这些记录是当前机器、当前模型、当前桌面内容下的短时测量，没有多轮统计分布，也没有覆盖所有应用、显示器和系统负载。完整流程的 FPS 也不等于端到端控制延迟或屏幕内容实际更新频率。模型执行得快，不代表识别一定准确；目标选择、跟踪和鼠标输出是否正确，还需要分别验证。这里的所有测速都关闭鼠标输出，原始记录中的 `input_enabled` 为 `false`。
