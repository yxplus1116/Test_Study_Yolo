# 能识别目标，但应用里不响应鼠标：排查记录

2026-09-12。用户补充现象：有红圈，`sent` 持续增加，个别应用内没有移动响应；提到管理员运行，但尚未明确指目标应用、本项目还是两者，也未提供具体 exe。

## 当前可以确定的结论

本项目只使用标准 Windows `SendInput`，发送 `MOUSEEVENTF_MOVE` 相对移动。`sent` 仅在 `SendInput` 返回 1 后递增。因此，在用户描述的连续增长时段，目标选择、鼠标按钮条件和控制线程确实至少多次到达了发送路径，Windows API 也报告插入事件成功。

这不等于指定应用已消费输入，更不等于画面已经按预期移动。当前 API 没有指定目标窗口参数；前台、鼠标捕获以及应用自身的输入处理会影响结果。现在还不能判定某个未知应用使用了何种屏蔽机制。

## 原因如何区分

| 观察到的证据 | 能作出的判断 | 下一步 |
|---|---|---|
| `sent` 不增加，显示 DRY RUN / WAIT / 无有效目标 | 尚未持续发送；不是“发送成功后应用不理会”的证据 | 检查菜单 3/4、类别、按键、目标、暂停与测量年龄 |
| `SendInput failed`，`attempted=1, injected=0` | Windows 插入事件失败 | 检查错误码、输入桌面、双方完整性级别；错误码不能单独识别 UIPI |
| 本项目完整性低于目标应用 | 存在 UIPI 权限不匹配条件 | 优先在双方均普通权限、且目标支持该运行方式时对照；对确需管理员的自有测试程序，另行明确双方运行身份 |
| `sent` 持续增长，前台是预览或其他程序 | API 成功，但当时激活对象不是预期应用 | 将调试框移离交互区域并重新激活目标应用；置顶不等于目标应用获得焦点 |
| `sent` 持续增长、前台正确，但仅特定应用无响应 | 更值得检查应用输入处理路径、光标捕获/归位行为、应用功能状态或对合成输入的处理 | 对照真实鼠标反应、应用官方输入设置、窗口模式；需要具体程序名称或自有程序的输入日志 |
| 桌面光标已移动，但目标画面不动 | 光标移动与应用视角/画面控制不是同一回事 | 确认目标应用该界面本来是否会随鼠标移动改变画面 |
| 画面有移动，但始终无法稳定对准 | 与完全没有响应不同，需要分析闭环 | 检查采集中心是否对应实际准星、目标关联、方向、延迟、应用灵敏度，再做调参 |

微软文档明确指出 `SendInput` 受 UIPI 限制，只能向相同或更低完整性级别的应用注入；UIPI 阻止时函数失败，返回值与错误码本身不能标明“原因就是 UIPI”。因此“管理员权限差异”是可检查的因素，但不能用它直接解释持续成功计数。[SendInput 官方说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

Windows 支持 Raw Input，应用可以注册原始输入并忽略传统鼠标窗口消息。这说明不同应用的输入链路可能不同；仅凭它使用 Raw Input，不能断言它必定拒绝本项目，也不能断言它存在防护拦截。[Raw Input 官方示例](https://learn.microsoft.com/en-us/windows/win32/inputdev/using-raw-input)

本次只增加诊断，没有替换鼠标发送方式，没有修改目标应用、权限或输入保护设置。桌面鼠标标定修正的是比例，不能让一个不处理该输入的应用突然开始处理。

| 23:10:52 身体控制 | 0 / 730 | 0 | 全部帧没有检测框 |
| 22:29:54 头部控制 | 1856 / 3507 | 37 | 有目标与按键条件间断成立 |

这三次均正常退出、没有采集错误，stderr 为空。它们没有前台应用记录，不能确认是否就是用户所述失效场景，也不能推翻用户补充的现象。

旧 `movement.csv` 的 `injected=0` 同时可能表示发送前门禁没有通过，并不自动等于 Windows 拒绝。新版加入 `attempted`：0 表示没有调用，1 才表示确实调用过 `SendInput`。

## 新版自动记录的诊断信息

正常从菜单 3/4 启动即可，不需要额外参数。日志只存本机每次运行目录 `.local/runlogs/menu-...`，通过菜单 **11 → 2** 打开；菜单 **11 → 6** 阅读此说明。

- `stdout.log`：启动时的本项目 PID、完整性级别、提升状态；每秒记录 sent、attempted、send_failures、按钮/新鲜度、前台 exe/PID/完整性级别及目标/输出状态。
- `movement.csv`：逐次控制回调的 frame、dx/dy、是否尝试发送、Windows 是否接受、Win32 错误码，以及调用前采样的前台 PID、记录时刻 elapsed_ms。`attempted=0` 时错误码 0 不代表执行过 API；`attempted=1, injected=1` 才代表接受成功。与上下文日志共用单调时钟起点；正常约每秒在回调中刷新缓冲，发送失败立即刷新，正常停止也会完整保存。
- `input-context.csv`：约每秒采样前台 exe 文件名/PID、双方权限级别、前台是否是本项目、光标位置及系统限制区域。只查进程身份和令牌元数据，不读窗口标题、应用内存或输入内容；查询失败标为 unknown 并记录 query_error。
- `frames.csv`：新增鼠标按钮条件、方向键门禁、测量新鲜度和测量年龄（毫秒，目标无效时为 −1）。这些是主循环采样，发送线程会再次检查。
- `summary.json`：新增 send_attempts / send_failures，保留 sent_count。发送失败会记录 stderr 并停止；异常退出可能没有最终 summary，应同时检查逐次日志。

前台进程权限在 PID 变化时查询，并至少每 10 秒刷新缓存；逐次移动只取前台 PID。焦点可能在采样之后改变，约一秒的上下文采样也会漏掉短暂切换，因此它提供定位线索，不是应用接收事件的证明。限制区域变窄或光标重复回中可作为调查线索，但不能据此自动判定输入被屏蔽。

## 下一次复现

1. 用更新后的菜单 3/4 选择正确类别，确认黄色框、红圈和 INPUT ENABLED。
2. 将菜单与置顶预览移出采集中央及操作区域，在目标应用中复现约 10 秒，观察 sent 是否在该时段增长以及真实鼠标在同一界面是否有效。
3. 松开鼠标按钮，菜单 10 停止，使日志完整落盘。记下发生问题的程序名称或 exe，以及它和本项目各自是否管理员运行。
4. 通过本机日志检查前台身份、双方完整性、attempted/injected 和目标状态，再决定应调整应用输入设置、权限配置还是本项目控制参数。当前缺少目标程序身份与对应复现数据，尚不能给出应用特定的根因结论。
